FRONTEND ROUTE AND ACTION BASELINE — PHASE 0
Captured: 2026-10-21. Scope: dashboard/ only.
Source of truth: src/app/router.tsx, src/components/layout/RoleSidebar.tsx,
src/lib/auth/permissions.ts, and the feature page/API hook implementations.
The route list below is mechanical, including public, protected, nested and
fallback routes. It does not replace the code's route guard.

ROLES AND AUTHORIZATION
Default homes: TEACHER /teacher; HOD /hod; AQA /aqa; FINANCE /finance;
PRINCIPAL and HEAD_OF_SCHOOL /principal; ADMIN /admin; ADMISSIONS /admissions;
MANAGER /manager; SUPER_ADMIN /superadmin; HEAD_OF_FINANCE /finance-group;
STUDENT and PARENT /app/mobile-guidance.
ProtectedRoute uses canAccessRoute for all authenticated paths. Prefix checks
in permissions.ts govern /teacher, /hod, /aqa, /finance, /principal,
/admissions, /admin, /reports, /academics, /exams, /analytics and /timetables.
RoleSidebar adds role-specific discoverability, not additional authorization.
ADMIN is not automatically group-scoped: session.user.scope === 'GROUP' is
authoritative in SchoolContextBar. Single-school users auto-select their one
visible school; multi-school users may select only assigned schools; group
users can return to All Schools. Selecting a school from a group-only route
opens /principal; changing school within school-scoped routes keeps the route.

EXISTING PEOPLE / SETUP ACTION AND PAYLOAD BASELINE
Users: /admin/users uses useAdminUsers; create, detail, edit, activate/lock,
password reset, membership and school move, deactivate/delete, and CSV import.
CreateUserPage sends email, role, firstName, lastName, phoneNumber, department
and isActive to useCreateUserMutation. The role/department selection, typed
danger confirmation, and password-reset feedback must survive.
Students: /admin/students and /admissions/students use useAdminStudentsPage;
pagination uses page/limit and existing GET /students supports search. Enrol
has six steps (Identity, Admission, Class, Guardians, Portal, Review). Submit
sends authUserId, names, dateOfBirth, gender, nationality, admissionDate,
classId, academicYearId and guardians through useCreateStudentMutation.
Admission number, intake stream, previous school and entry level are UI fields
but were not in that payload at baseline; this refactor must not silently
alter that contract. Student detail has identity, guardians, portal,
attendance, performance, finance, discipline and audit panels. Import uses
existing /students/import preview/commit and class assignment payload.
Admissions: inquiry, applicant search/directory, profile, assessment/offer,
stage transitions, conversion, student registry/enrolment and analytics are
separate from the admin user directory. Existing mutations in
admissions.hooks.ts retain their bodies (applicant body, {toStage,note},
assessment/offer body, {decision,note}, {admissionDate}).
Academic setup: /admin/academic/setup links years, terms, classes, subjects,
class-subject/teacher assignments, grading, assessment types, stage config,
cross-stage promotion; departments has an existing route too.
Other major families: teacher, HOD, AQA, finance, principal, manager,
superadmin, e-learning, exams, reports, analytics, timetables, shared app.
Their route components and actions remain in the code and are not rewritten
by phases 1-3.

BASELINE USABILITY FINDINGS
1. The old sidebar mixed directories with create/import actions, and long
   sections competed for attention.
2. UsersTable supplied onSearch, but AdminDataTable did not render the input.
3. Student Registry had pagination but no search control despite the existing
   GET /students search query.
4. Admissions Student Registry pointed Import Students at a missing
   /admissions/students/import route, although the backend allows ADMISSIONS
   to use the same import endpoint.
5. Academic Setup cards were flat, without dependency orientation.
6. The top bar's term button was a static label that implied interactivity.
7. AdminShell's environment/status header uses static display values; these
   are not live backend health indicators and require separate product work
   if real-time status is desired.
