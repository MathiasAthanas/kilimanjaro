KILIMANJARO DASHBOARD — FRONTEND USABILITY AND FLOW REFACTOR
Version: 2026-10-21
Status: planning document; no implementation is authorized by this file itself.

PURPOSE
Make the existing Kilimanjaro web dashboard easier to navigate and operate, using
the task flow observed in the owner's hosted KEMS/Zeraki Analytics app as a UX
reference. This is NOT a clone, rebrand, feature expansion, data migration, or
backend project. The useful reference pattern is: choose the school, find a
record in a list, open the record, perform a clearly named action, and see the
related tasks in a local context menu. The hosted app's visual design, data
model, and permissions are not specifications for Kilimanjaro.

HOW TO USE THIS FILE
1. Work through phases 0-9 in order. Copy ONE complete "PROMPT" block at a
   time into a new coding request. Do not ask an agent to implement the whole
   plan in one pass.
2. At the end of each phase, review its acceptance checklist and the agent's
   route/role parity report before starting the next phase. Stop if a feature,
   access rule, color, or existing action disappears.
3. No phase implicitly authorizes work on the next phase. If a phase exposes a
   backend problem, document it; do not edit backend code or the database.
4. Where the prompts say "existing", inspect the repository at execution time.
   This plan describes the code as observed on 2026-10-21; later changes may
   supersede individual file locations.
5. Keep ordinary commits/PRs clean: no demo seed data, credentials, screenshots
   of private school data, generated browser profiles, or local environment
   files. Never place the hosted-app login credentials in code or this plan.

NON-NEGOTIABLE CONTRACT FOR EVERY PHASE
- Edit dashboard/ only. Do not modify backend/, API contracts, database schema,
  seeds, Docker, PM2, environment files, or authentication behavior.
- Preserve every existing feature, business rule, field, validation, status,
  permission, route, deep link, mutation, export, import, report, and role
  workflow. Reorganizing a link must not remove access to its destination.
- Preserve the existing Kilimanjaro color values, typography, icon language,
  and branding. Use dashboard/tailwind.config.ts and
  dashboard/src/styles/tokens.css as the color source of truth. Do not copy the
  hosted app's palette or add a new palette. Layout and spacing may change.
- Keep server-provided school scope authoritative. ADMIN may be school-scoped;
  do not infer group access from its label. Preserve the All Schools/group view,
  school switcher, multi-school membership, and existing route authorization.
- STUDENT and PARENT remain mobile-primary in the current web app. Do not
  invent a new web experience or reroute them away from mobile guidance.
- Favor existing components, hooks, routes, and API calls. Add frontend-only
  presentation helpers where needed. No fake data, no dead buttons, no hidden
  forms, and no action that silently changes semantics.
- On every screen: clear title and school/term context where already available;
  list/search first for record management; one primary action; secondary tasks
  grouped locally; breadcrumbs/back path; loading/empty/error states; clear
  success/error feedback. Do not require extra clicks for frequent tasks merely
  to imitate the reference app.
- Preserve accessibility: keyboard navigation, visible focus, semantic
  headings, labeled controls, active navigation indication, responsive layout.
- Compare before/after route and action inventories. Run the relevant tests,
  typecheck, lint, and build. Report commands and results, including failures.
- Stop after the requested phase and report changed files, route/action parity,
  tests, risks, and what the next phase should tackle.

REFERENCE OBSERVATIONS (not requirements to copy pixel-for-pixel)
- Hosted KEMS displayed a narrow main navigation, a school selector, and
  horizontal task tabs inside a section. The current Kilimanjaro app already
  has a sidebar and school selector; improve their relationship rather than
  replacing their functionality.
- Classes: list first (class, boys, girls, students, supervisor), then Manage
  for streams and Class list for roster; Add New Class is a contextual task.
- Students: Search Student and Add Student are adjacent; new-student details
  are staged in a visible wizard; spreadsheet upload is an alternate path.
- Teachers: directory first, Add New Teacher nearby, and spreadsheet entry is
  an alternate path. Kilimanjaro's existing user/staff model must remain intact.
- Subjects: related setup tasks (departments, subject groupings, compulsory
  subjects) are discoverable together. Do not add a KEMS-only data concept if
  Kilimanjaro has no equivalent existing feature.

TARGET INFORMATION ARCHITECTURE
Global layer: school/group context, current role, global search, notifications,
profile/help, and the major work areas actually available to that role.
Section layer: a small set of task tabs/links that reflect the active area;
the same concept should work as a compact menu on narrow screens.
Record layer: list/search -> detail -> related work -> clear return path.
Setup layer: a dependency-aware "where do I start?" explanation using only
existing actions: school/year/term context -> departments/subjects -> classes,
streams/combinations/pathways -> class subjects/teaching assignments -> people
and enrolment -> day-to-day academic/finance operations. This is orientation,
not a new required sequence or new backend validation.
Role layer: show the steps a role is allowed to perform; preserve authorized
cross-role links and existing approvals. Never show an unauthorized action and
never remove an authorized one.

FINAL DEFINITION OF DONE
- A user can tell which school, role, section, record and task they are in.
- For master data, the common path is directory/list -> add/import or open ->
  detail -> related task -> back; the existing forms and results are intact.
- Different roles see an appropriate path to their existing work; no role gains
  or loses access, and group/school boundaries are preserved.
- Every Phase 0 route and action remains functional and discoverable, including
  long-tail features and direct URLs.
- Kilimanjaro branding, all color values, domain logic, API contracts and
  backend remain untouched. Tests and human walkthroughs support this claim.
